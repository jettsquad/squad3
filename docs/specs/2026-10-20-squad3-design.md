## 0. 一句话

> **Squad 自己当宿主。** Claude Code、Codex、DeepSeek Harness（dsh）都只是坐在桌边的席位，谁也不是谁的底座。

2.x 是「dsh 的一组插件」：dsh 是宿主，Squad 借它的插件框架、会话日志、存储、凭据、Web 服务和界面插槽，席位由 dsh 以子进程拉起。Squad 3 把这层关系倒过来：Squad 是一个独立的桌面应用，dsh 和另外两个 CLI agent 平级，都是被调用的一方。

需求本身（2.x 需求文档 §0–§3 的场景与功能）**不变**。变的是形态。

## 2. 与 2.x 的关系

### 2.1 代码：移植，不是重写

2.x 约 3.2 万行，分布在 14 个包里。按依赖性质分两类：

| 类别 | 内容 | 处理 |
|---|---|---|
| **核心逻辑**（几乎不碰 dsh） | `shared`（议程、议程状态机、检查点阈值、TeamPlan、连接与注入规则、席位失败文本、用量……）、`context` 的窗口与时间线、`secretary` 的议程/检查点/终止交接、`reasoning`（Lil X）、`console` 里的纯函数（点名解析、命令解析、名册漂移、议程裁定、团队设计器） | **原样搬，连同全部测试**。测试是搬迁的验收标准，与 2.0 从 1.x 搬运时同一条规矩 |
| **管道**（全是 dsh 的基础设施） | cordis 插件框架、`dsh-storage-domain`、`dsh-credentials`、`dsh-subagent` / `dsh-subprocess`、`dsh-commands`、`dsh-host-webserver`、各种 `dsh-client-ui-*` 插槽与零件 | **换掉**，见 §4–§9 |

**来源标注**：3 里每个从 2.x 搬来的文件，头部注明 `移植自 Squad 2.x <包>/<文件> @ <commit>`。D2 决定了两边会各自演进，2.x 修了核心逻辑的 bug 时，靠这行判断 3 要不要跟。

### 2.2 不重走的路

2.x 文档里记下的「被否决的方案」和踩过的坑（订阅模式下外来模型名、`CLAUDE_CONFIG_DIR` 隔离、codex 的 `wire_api`、stderr 里的失败原因、「测试通过、真跑失败」……）全部继承。它们是 2.x 最贵的资产，比代码更贵。

## 3. 形态：回到 Electron —— 对 2.0「放弃 Electron」的回应

2.0 架构文档 §2 明确放弃了 Electron，理由有三。3 回到 Electron，必须逐条回答，否则就是在重走一条被否决的路。

| 2.0 放弃 Electron 的理由 | 当时成立吗 | 3 的处境 |
|---|---|---|
| **IPC 膨胀**：1.x 的 `electron.ts` 有 1,758 行，几乎全是每个通道的四道校验 | 成立 | 3 只开**一个类型化通道**（§9）：所有方法列在一张表里，每个方法一个 schema，校验写一次。2.x 的 `client/api.ts` + `wire.ts` 已经是这个形状，只是传输从 `fetch` 换成 IPC |
| **UI 无法插件化**：加一个面板要同时改主进程、preload、渲染层 | 成立 | 2.x 要插件化，是因为它住在 dsh 的插槽里，只能这么做。3 是一个完整应用，**没有第三方插件**，不需要运行时插件化。需求 N7「一切皆插件」在 3 里改写为「**按能力切片**」：每个能力是一个目录，含服务、IPC 方法和界面，加一个面板只动这一个目录 |
| **想从任何设备的浏览器访问**（需求 N1） | 成立 | **3 放弃这一条**。见 §15 待定项 Q1，需要你确认 |

回到 Electron 还**顺带解决了 2.x 自己记下的一个隐患**。`console/src/http.ts` 开头写道：localhost 上的 HTTP 路由，任何有 shell 的东西都够得着，包括手里有 Bash 工具的席位。所以 2.x 不得不把「能开轮次」的操作和「只是配置」的操作分开对待。Electron 的 IPC 只有渲染进程够得着，**席位的子进程碰不到它**——「没有模型坐到主持位上」这条不变量从纪律变成了拓扑事实。

## 4. 整体结构

```
┌──────────────────── Squad 3（Electron）─────────────────────┐
│                                                              │
│  渲染进程（React）                                           │
│    主工作台 / 团队与席位 / Agent 库 / 连接 / 判据 / 设置     │
│        │  window.squad.invoke(method, payload)               │
│        │  window.squad.on(event)          ← preload 唯一桥   │
│  ──────┼──────────────────────────────────────────────────── │
│  主进程（Node）                                              │
│    ipc        方法表 + schema 校验 + 事件推送                │
│    table      团队、名册、轮次编排、议程状态机               │
│    context    窗口切片、时间线、检查点折叠                   │
│    secretary  议程草案、检查点正文、终止交接、协助           │
│    reasoning  Lil X 判据库、捕获、提炼、投放、代理           │
│    library    Agent 库、连接、提示词片段、设置               │
│    store      团队日志（JSONL）、配置（JSON）、原子写         │
│    vault      凭据（safeStorage）                            │
│    seats      席位适配器层 ─┬─ claude-code                   │
│                             ├─ codex                         │
│                             └─ dsh                           │
│    extras     材料解析、朗读、听写、通知、CLI 版本管理       │
└──────────────────────────────┬───────────────────────────────┘
                               │ 子进程（每回合一个，跑完即销毁）
                 claude  ·  codex  ·  dsh --profile headless
```

### 4.1 模块之间怎么连

**建议不再用 cordis**（§15 Q2）。2.x 用 cordis，是因为要以插件身份住进 dsh 的插件树。3 没有这个需要：模块数量固定、没有第三方插件、不需要热重载。改成普通的 TypeScript 模块，在一个组合根（`main/compose.ts`）里按依赖顺序显式构造。

2.x 的「插件之间只能通过服务说话、不能 import 对方实现」这条墙保留，换个方式执行：每个模块只导出一个接口和一个工厂函数，eslint 的边界规则拦住跨模块直接 import 内部文件。`shared` 和 `seat-runtime` 两个「库不是插件」的例外照旧。

## 5. 席位适配器层

这是 3 最核心的新东西，也是使用者初衷的落点：**桌子只认一个接口，不认识任何具体 agent。**

### 5.1 接口

```ts
interface SeatAdapter {
  readonly backend: "claude-code" | "codex" | "dsh"
  /** 这个后端支持什么。不支持的能力在请求时被拒绝，而不是收下再悄悄不执行（2.x §9.1） */
  readonly capabilities: {
    readonly toolFilter: boolean      // codex: false
    readonly persona: boolean         // 不支持时并入 prompt 正文
    readonly webAccess: boolean
    readonly permissionModes: readonly PermissionMode[]
  }
  /** 探活：5 项检查，结论三值（通过 / 不完整 / 失败），沿用 2.x §7.8、§10.5、§14.4 */
  check(connection: ResolvedConnection): Promise<AgentCheckReport>
  /** 一回合。one-shot：一个新进程，跑完即销毁 */
  start(request: SeatRequest): SeatRun
}

interface SeatRequest {
  readonly cwd: string                     // 团队的项目文件夹
  readonly prompt: string                  // 已装配好的上下文 + 本轮指令
  readonly persona?: string
  readonly connection: ResolvedConnection  // 后端、认证方式、端点、模型、已解析的凭据
  readonly permissionMode?: PermissionMode
  readonly toolFilter?: ToolFilter
  readonly reasoningEffort?: ReasoningEffort
  readonly signal: AbortSignal
}

interface SeatRun {
  /** 过程中的活动：在用什么工具、说了多少字。用于「正在做什么」和沉默看门狗 */
  readonly activity: AsyncIterable<SeatActivity>
  /** 最终结果。发布后绝不 reject（2.x seat-runtime 的 run-handle 契约） */
  readonly result: Promise<SeatResult>
}

interface SeatResult {
  readonly text: string        // 已剥掉 think
  readonly failed: boolean
  readonly failure?: string    // 失败原因：解析器所知 → stderr 末几行 → 退出码（2.x §9.9）
  readonly usage?: SeatUsage   // token、费用
  readonly exit: { code: number | null; signal: string | null }
}
```

### 5.2 三个适配器

| 后端 | 调用方式（沿用 2.x，已对真 CLI 验过） | 要点 |
|---|---|---|
| claude-code | `claude` 命令行，`stream-json` 输出 | api-key 席位用**临时 `CLAUDE_CONFIG_DIR`**，否则本机登录态会压过连接的密钥（2.x §14.2）；订阅模式下只放行 Anthropic 命名空间的模型名（§1.3）；工具围栏默认禁 Task/Agent；skill 经 `--plugin-dir` 交付 |
| codex | `codex exec --cd <dir> --json --skip-git-repo-check` | 权限走 `-c approval_policy=…`；端点走 `-c model_providers.<id>.base_url`，`wire_api` 只能是 `responses`（§14.1）；没有工具围栏，能力里如实声明 |
| dsh | `dsh --profile headless <任务>` + 一次性 `--patch` | 端点和模型写进临时 patch，**密钥只写变量名**，用完即删（§12）；可执行文件路径可配置（dsh 常常不在 PATH 上） |

三个适配器共用的部分（取消如何到达子进程、沉默看门狗、输出收集与上限、退出后读回）放在 `seat-runtime` 库里，直接从 2.x 的 `@squad/seat-runtime` 移植。2.x 用它把 seat-claude-code 从 406 行降到 217 行。

dsh 的命令行接口还在 alpha 阶段，所以它的调用细节只允许出现在 `seats/dsh/` 里。dsh 一升级，只改这一处。

### 5.3 Windows 上要额外处理的事

2.x 主要在 macOS 上开发和验证（文档里的路径是 `/Volumes/...`），而这台机器是 Windows。以下几点 2.x 没有碰到过：

- **`.cmd` 包装**：npm 装的 `claude`、`codex` 在 Windows 上是 `.cmd` 文件，`spawn` 不加 shell 时找不到。要么解析出真实的 `.js` 入口用 Node 跑，要么显式走 `cmd.exe /c`。前者更好，因为参数不经过 shell 转义。
- **进程树清理**：取消一回合时，必须杀掉席位起的整棵进程树。Windows 上用 Job Object 或 `taskkill /T /F`。2.x 依赖的 `dsh-win32-process` 不再可用，要自己做。
- **路径规范化**：大小写不敏感、盘符大小写、`\` 与 `/`。团队的项目文件夹从建立起就存规范形式（2.x §8.2 的教训）。
- **通知**：2.x 的完成通知只有 macOS（`osascript`）和 Linux（`notify-send`）。Electron 的 `Notification` 三平台通用，顺手补上。

## 6. 存储

### 6.1 数据目录

Electron 的 `userData`，Windows 上是 `%APPDATA%\Squad`。与 2.x 的 `~/.dsh-squad-dev` **完全分开**（D5，也是 2.0 当年「独立 appId / userData」那条硬约束的重演）。

单实例：Electron 的 `requestSingleInstanceLock()`，加上数据目录里的锁文件。2.x 的 `ui.mjs` 记下过两个进程共用一个 home 写坏 session 日志的事故，这条守卫必须在。

### 6.2 团队日志：Squad 自己的事件词汇

2.x 的团队记录**被迫拆成两处**：发言进 dsh 主持人节点的 session 日志，检查点、议程、轮次进 storage domain。原因是 dsh 的持久化读路径拒绝任何它不认识的事件类型（2.x 技术设计 §5）。装配时再把两处合并成一条流，一致性靠自己保证。

3 里**日志是自己的**，这个限制消失了：

```
%APPDATA%\Squad\teams\<teamId>\log.jsonl     追加写，一行一个事件，带递增 seq
```

所有团队级事件（主持人发言、席位回复、检查点、作废、议程草案与确认、节点状态变化、决策、引用、材料）都进同一条日志。`context` 不再需要「合并两处」那一步。

**事件类型是闭合列表**，读到不认识的类型就报错，不跳过。这是 2.x `context/README.md` 里「渲染层不许有 catch-all」那条规矩在存储层的版本。

### 6.3 「席位看见了什么」终于能存下来

2.x 技术设计 §10.10 留了一个悬案：席位不是 dsh 的 Agent，没有自己的 session，于是「model-visible means logged」在席位层不成立，只能靠「可重建」凑合。当时列了三个选项，没定。

3 里日志是自己的，**选 (a)**：每回合发给席位的完整 prompt 作为 `seat/request` 事件写进团队日志（或旁边的 `requests.jsonl`，按 seq 关联）。代价是日志变大，换来的是任意时刻都能回答「这个席位这一回合看见了什么」——需求文档全局验收的最后一条。

### 6.4 配置与资料库

| 内容 | 位置 | 说明 |
|---|---|---|
| 团队索引、名册、用量 | `teams\<teamId>\team.json` | 用量**每轮写盘**，不在关机时（2.x §10.1） |
| Agent 库、连接、提示词片段、设置 | `library\*.json` | 软删除照旧 |
| Lil X 判据库 | 用户选的目录，默认 `%APPDATA%\Squad\lil-x` | **纯文本、git 可管、离开 Squad 仍可读**，格式与 2.x 相同 |
| 议程报告 | `<项目>\.squad\reports\` | 与 2.x 相同 |

所有 JSON 写入走「临时文件 + rename」的原子写，带 schema 版本号。

## 7. 凭据

2.x 用 dsh 的 `ctx.credentials`。3 用 Electron 的 `safeStorage`（Windows 上是 DPAPI，macOS 上是钥匙串）。

继承 2.x 的四条规矩：

1. 配置里只存**引用**，不存值
2. 界面上只显示「已配置 / 未配置」，**值永远不到渲染进程**
3. 编辑时密钥框为空，空就是「不动已存的那把」（§9.8）
4. 支持「这把 key 已经在环境变量里了」：勾上后填变量名，不存值（§7.6）

## 8. 界面

渲染进程用 React，布局按 2026-10-20 讨论时的三张草图：左栏团队与资料库、中间讨论区和输入框、右栏议程与上下文；另有启动画面和托盘。

| 2.x 用的 dsh 零件 | 3 的替代 |
|---|---|
| `Button`、`Input` 等基础组件 | 自己的一套小组件 |
| `MarkdownText`（GFM 表格、代码高亮、复制按钮、KaTeX） | `react-markdown` + `remark-gfm` + `rehype-katex` + 代码高亮 |
| 原生文件夹选择（`ctx.directoryPicker`） | Electron `dialog.showOpenDialog`，三平台都是系统对话框 |
| dsh 的侧栏、工作区、会话 | 不需要。团队本身就是左栏的一级对象 |
| 每 2 秒轮询快照 | 主进程**推送**变化事件；渲染进程按需拉取 |

2.x 的 `console/src/client/` 下大部分组件（讨论区、席位条、议程、上下文面板、材料、Agent 库、连接、判据、提示词片段、用量……）去掉 dsh 依赖后可以搬过来。界面文字的中英两套词典（`locale.ts`、`locales.ts`）一起搬。

## 9. IPC 契约

```ts
// shared/wire.ts —— 主进程和渲染进程都 import 这一份
export const methods = {
  "teams.list":      { input: z.object({}),                    output: SquadSnapshot },
  "teams.create":    { input: CreateTeamRequest,                output: z.object({ teamId: z.string() }) },
  "round.say":       { input: SayRequest,                       output: z.object({ commandId: z.string() }) },
  // …… 2.x client/api.ts 里的约 50 个方法，一一对应
} as const
```

- preload 只暴露两个函数：`invoke(method, payload)` 和 `on(event, handler)`
- 主进程收到调用，先按表里的 schema 校验输入，不认识的方法名直接拒
- 拒绝时**原样带回宿主给的理由**（2.x `api.ts` 的 `call()`：「订阅模式不使用自定义端点」这句话本身就是拒绝的全部价值）
- 渲染进程：`contextIsolation: true`、`sandbox: true`、`nodeIntegration: false`

斜杠命令（`/squad-new`、`/squad-say` 等 11 条，逐条见 `docs/parity.md` §C）在 3 里变成输入框里的命令，由渲染进程解析后走同一张方法表。它们不再是「唯一的入口」，而是快捷方式。

## 10. 功能清单：2.x → 3

这张表从 2.x 的代码（`console/src/client/api.ts` 的方法表、斜杠命令、各包源码）盘点而来，**是 3 的验收清单**。阶段 0 要把它细化成逐条可勾选的 `docs/parity.md`，每条附 2.x 的出处。

| 领域 | 2.x 具备的功能 | 3 的承接模块 |
|---|---|---|
| **团队** | 建团（从 Agent 库勾人、指定秘书、选项目文件夹并校验存在）、改名、排序、解散（说明留下什么）、持久化与重启恢复（恢复失败报出来再跳过） | `table` |
| **席位** | 加席、删席（删秘书要确认）、改连接与上限、重新关联到 Agent 库模板、名册漂移检测、席位状态（工作中 / 待命 / 警告，悬停看本轮指令）、沉默看门狗与心跳 | `table` + `seats` |
| **发言** | `@` 点名（只认开头、名字边界、打错即拒）、广播、引用旧发言、附材料、取消或撤回一条指令、重发被中断的指令、叫停、并发轮次守卫、按下即清空输入框 | `table` + 界面 |
| **讨论记录** | Markdown 渲染、发言人色标、「带了几行讨论」、向前翻页加载更早记录 | `context` + 界面 |

## 11. 从 2.x 导入数据

### 11.1 读哪些

| 2.x 数据 | 位置（2.x 的 `DSH_HOME`，开发态默认 `~/.dsh-squad-dev`） | 导入到 |
|---|---|---|
| 团队、名册、议程状态 | storage domain `squad_table`、`squad_teams` | `teams\<teamId>\team.json` + 日志 |
| 讨论记录 | dsh 的 session 日志（每支团队的主持人节点一份 JSONL） | `teams\<teamId>\log.jsonl` |
| Agent 库、连接、提示词片段、设置 | `squad_agent_templates`、`squad_connections`、`squad_prompt_blocks`、`squad_settings` | `library\*.json` |
| Lil X 判据库 | `lil-x` 目录 | 原样复制，或直接指向原目录（§15 Q6） |
| 凭据 | dsh 的凭据存储 | **默认不导入值**，只导入引用；导入后在界面上标「需要重新填写」（§15 Q5） |

讨论记录要读 **dsh 的 session 日志格式**，而这个格式本身有版本（dsh 自带 v0→v1→v2→v3 的迁移包）。导入器只接受它认识的格式版本，不认识就拒。

### 11.2 规矩：全部继承 2.x 的 `@squad/migrate`

- **有任何一处读不懂，这支团队就不迁**。拒绝按团队，不按整批
- **默认试运行**：只报告会迁什么、读不懂什么，不写一个字节；真迁要显式确认
- **迁完回读**：不靠「没抛错」当成功，把窗口读回来核对检查点和产出
- **turnId 原样保留**，否则检查点的 `coversUpTo` 会指向不存在的边界
- **作废状态跟着走**，主持人否决过的检查点不能因为迁移而复活
- **事件类型没有 catch-all**：每个 2.x 事件类型要么被处理，要么显式列为「不携带内容」，要么被报告
- 2.x 的源数据**只读**，导入过程不改动它的任何文件

导入入口放在首次启动的引导里，也可以在设置里随时再跑。

## 12. 不变量

继承 2.x 架构 §8，以及议程图文档 §3.9 对它的修订：

1. **席位之间没有直接通道。** 甲要看见乙说了什么，只能由桌子注入。独立作答因此是拓扑事实
2. **进入模型请求的内容必须能从日志重建。** 3 里通过 §6.3 落实到席位层
3. **判据只关于过程，不关于结论**
4. **没有模型坐到主持位上**，除非使用者对这份议程明确开启了「由 Lil X 代理」。开启后 Lil X 可在名册内选人，但派发仍由桌子的确定性代码校验并执行；它不能加人、改目标、改验收基线
5. **判据的入库与生效需要人裁定**
6. **绝不静默失败。** 装不下、没生成、校验失败、读不懂，一律明确报错
7. **能配不等于能用。** 存得下、显示得出、然后被忽略的设置，比没有这个设置更糟（2.x 撞了四次）。每个配置项都要有一条测试证明它真的到达了席位进程

## 16. 阶段 1 实现记要（2026-10-20）

门控通过：在 Windows 上，界面里建了一支 1 人团队，真实的 `claude` 席位答了三轮（第二轮凭上下文窗口答出上一轮的结论），一轮被叫停；重启后团队、讨论、用量都在；日志里查得到指令、席位拿到的完整 prompt、回复。

与上文的出入，以这里为准：

- **§5.1 `SeatRun` 的形状。** 没有用 `activity: AsyncIterable`，改成请求里的 `onActivity` 回调加 `cancel()`。一个席位一轮只有一个消费者（桌子），回调更简单，也不需要处理没人读时的背压。
- **prompt 走标准输入，不走命令行参数。** Windows 的命令行上限是 32,767 字符，带着整段讨论的 prompt 几轮就会超。2.x 在 macOS 上把 prompt 放在 argv 里，那边的上限约 1MB。实测 `claude -p` 不带 prompt 参数时从标准输入读，中文完好。codex、dsh 适配器在阶段 2 要各自确认同样的做法。
- **`.cmd` 包装不经过 shell。** 适配器读 npm 生成的 `.cmd` 文件，找出真正的 `.exe` 或 `.js` 入口直接运行（§5.3）。这样 prompt 里的引号、百分号、换行都不会被 `cmd.exe` 改写。
- **上下文窗口是占位实现。** `src/main/context` 现在把此前的全部讨论原样带给席位，没有折叠和检查点。阶段 2 用 2.x 的 `packages/context` 及其测试替换。
- **一个只有真实运行才能发现的坑。** Electron 44 自带的 Chromium 152 里，`scrollIntoView()` 返回 Promise。界面里一个用箭头函数简写的 effect 把它当成返回值交给了 React，下一次渲染时整个窗口变空白。类型检查、构建、全部测试都是绿的。现在加了一条 lint 规则，禁止 effect 用表达式简写。
- **新发现的 2.x 功能：席位会话续接（`--resume`）。** 阶段 0 盘点时漏掉了，已补进 `docs/parity.md` §B，阶段 2 做。

## 17. 阶段 2 实现记要（2026-10-20）

搬了 2.x 的上下文装配、秘书任务、指令队列、席位会话续接、Codex 与 dsh 两个后端、席位活动跟踪、共享 skill、`@` 点名与斜杠命令的解析，测试原样跟着搬（592 个全绿）。在真实应用里用 Claude Code、Codex、dsh 三个后端走过一遍。

与上文的出入，以这里为准：

- **团队日志就是全部记录**（§6.2 落实）。检查点和作废是日志里的两种事件，`merge.ts` 照旧按 `coversUpTo` 把检查点插回正确位置——日志里的位置 ≠ 覆盖范围，因为秘书写检查点时团队不停。
- **发言是指令队列，不是「一轮」**。2.x 后来已经这样改了：不同席位并行，同一席位按发出顺序一条条答（它要续接自己的 CLI 会话，两轮同时续接会互相丢内容）。阶段 1 那个「一桌只跑一轮」的守卫因此取消。
- **独立 / 累积作答**在 2.x 里已经是议程阶段的 `contextMode`，随议程放到阶段 4。
- **三个后端的 prompt 都走标准输入**：Codex 和 dsh 的 prompt 参数写成 `-`，2.x 的命令行组装函数一行没改。
- **dsh 心跳插件改成内置源码**，启动 dsh 席位前写到数据目录。打包后的应用里没有 `.ts` 源文件可供 dsh 子进程加载。
- **找 dsh**：在设置界面（阶段 3）之前，用环境变量 `SQUAD_DSH_BIN` 指定位置。
- **退出时被打断的指令记为「中断」**，不写回复、不写叫停；重启后由主持人决定是否重发。这是 2.x `commands.ts` 的语义，阶段 2 的第一版错记成了「叫停」，真实运行时发现并改正。
- **Windows 适配**：Codex 在 Windows 上用 `powershell.exe -Command '…'` 跑命令，活动显示时把这层外壳剥掉；`/squad-new` 认 `J:\` 这样的绝对路径。

两个观察，留给后面的阶段：

- **Claude 席位默认跑不了 shell 命令。** 默认权限模式 `acceptEdits` 允许改文件，但 shell 命令要人批准，而 `-p` 模式下没有人能批准。和 2.x 一致；Agent 库（阶段 3）让每个席位选权限模式。
- **续接会话在隔离模式下不一定更便宜。** 实测一次续接的花费（0.049 美元）比新开（0.028 美元）还高。2.x 量出续接省钱时，席位还带着宿主的全部配置（新开要建 6.6 万 token 缓存）；现在默认隔离，新开只建约 6 千。`reopen.ts` 的阈值值得在阶段 3 用真实数据重新量一次。

## 18. 阶段 3a / 3b 实现记要（2026-10-20）

3a 是连接、Agent 库、设置、凭据库和名册操作的后端；3b 是它们的界面。2.x 的连接规则、模板、名册规则（`roster.ts`）、模板同步（`seat-sync.ts`）、Agent 测试的报告格式连同测试一起搬了；`checkAgent` / `probeSeat` 改写后搬进 `main/agent-check`。在真实应用里走过一遍（`parity.md` 里打了勾的行）。

与上文的出入，以这里为准：

- **凭据库**（§7 落实）：环境变量优先且只读；其次是数据目录里的 `vault.json`，值用 Electron `safeStorage` 加密（Windows 是 DPAPI）。环境变量占着的名字，这里拒写，不接受「存了但读出来是另一个」。系统加密不可用时拒存，不明文落盘。删连接时，存在这里的密钥一起删。
- **名册操作在 table 里**，不再分在 console 的 HTTP 处理函数里：建团（从 Agent 库挑成员，或手写席位——`/squad-new` 用后者）、加、删、改连接与上限、重新关联、按模板同步、改名、排序、解散。改名册在有命令在跑时一律拒，和 2.x 一样。
- **连接在每一轮开跑时现查**，查不到就让这一轮失败并说明，不退回本机登录。换连接或换后端会丢掉这个席位的续接会话：会话属于原来那个模型。
- **上限在开跑之前查**（2.x `capReached`）。被拦下的那一轮在记录里是一条失败的回复，写明哪个上限到了；没有起子进程，所以也没有「看它这一轮拿到了什么」。
- **解散**：`team.json` 里记一个 `disbandedAt`，团队文件夹留着，启动时不再载入。有命令在跑时拒。
- **Agent 测试的第 ① 项**不再问「dsh 里注册没注册 provider」，而是问「有没有这个后端的适配器、连接在不在、后端对不对得上」；第 ② 项用适配器自己的 `locate()`，和开跑时找命令行工具的路径一模一样（dsh 读设置里的路径）。第 ⑤ 项在一个用完即删的临时文件夹里真问一句，90 秒没答复就明说是超时。

- **讨论记录读 2.x 自己的记录文件**（`squad-records/<id>.jsonl`，2.x 的 `log.ts` 写），不读 dsh 的会话日志：§11.1 写的时候 2.x 还把记录放在 dsh 会话里；8e96d9c 已经搬到自己的文件，dsh 那份格式会随 dsh 升级变。没有记录文件的团队拒绝导入，并说清怎么让 2.x 建出它。
- **记录行变成 3 的类型化事件**：主持人的话 → 指令（turnId 当指令 id），席位的话 → 答复（答的是前面最近的那条指令；带「答 HH:MM「…」」标签的，按标签找它答的那条），「系统」→ 系统说明，「Lil X（代主持人）」→ 代理发言。2.x 用 ⚠️ 开头标失败、用「被叫停，未答完」标打断，照这两个标记还原。时间是说话的时间，不是导入的时间。
- **2.x 的「场次」导入后是所属团队下的一场会话**（§29）。在会话做回来之前，场次各自成了一支团队、名字带「那一场」；这些在启动时按导入记录里写的来源归回所属团队，只做一次，并记一条。
- **不在名册上的发言人**（换过人或改过名）按「已离席的成员」导入，报告里说一声——这不是读不懂，读得懂，只是那个人不在了。
- **进行中的议程或草案**这一版不带：有就拒绝那支团队，请先在 2.x 里收尾。其余不带的东西（席位的 CLI 会话、2.x 输入框里勾着没发的）在报告里逐条说明。
- **密钥不带**（§15 Q5）：连接带着引用过来，显示「密钥未配置」，在「连接」里填一次就行；两条连接共用一个引用的，填一次两条都有。
- **回读**：先按行数核对写进去的日志，再让正在跑的桌子按重启的方式把团队接过来（`table.adopt`）——它读不进来就算失败，写了一半的文件夹删掉，下次照样能重试。
- **重复导入**：已经在 3 里的团队、Agent、连接跳过，不覆盖。
- 2.x 那边**只读**：测试和实测都核对过导入前后 2.x 的文件一个字节没变。
- 导入的是那一刻的快照：之后在 2.x 里继续的讨论不会自动同步过来。

## 28. 阶段 6b 实现记要：安装包（2026-10-21）

electron-builder（`electron-builder.yml`）。`npm run dist:win` 出 Windows 安装包，`npm run dist:mac` 在 Mac 上出 dmg。

- **Windows**：NSIS，按用户安装（装到 `%LOCALAPPDATA%\Programs\Squad`，不弹管理员确认），可以改安装位置，开始菜单和桌面各一个快捷方式。快捷方式带应用 id `com.squad.desktop`——Windows 有了它才肯显示 Squad 的通知（§25）。卸载**不删**数据目录：团队、Agent 库和密钥是使用者的，不是程序的。
- **macOS**：dmg；`NSMicrophoneUsageDescription` 写进 Info.plist，否则 macOS 直接拒绝麦克风，听写录到的是静音。要在 Mac 上构建，Windows 上出不了 dmg。
- **下载工具**的脚本放在包外（`asarUnpack`），由席位的 CLI 用 Squad 自己的可执行文件以 Node 模式起；`download-tool.ts` 先找包外那一份。实测打包后的程序里下载工具能用。
- **图标**在代码里画（一张圆桌、三个席位），`build/icon.png` 是同一张图放大到 512 像素。
- **没有代码签名**：Windows 的 SmartScreen 和 macOS 的 Gatekeeper 都会提示来源不明。签名要证书，是另一件事。
- 安装版和开发版用同一个数据目录（`%APPDATA%\Squad`），同一时间只能开一个。
- **实际安装**（2026-10-21）：静默装到自选目录（`"Squad Setup ….exe" /S /D=<目录>`）。快捷方式的应用 id 对，程序能跑。系统通知：Windows 报告 Squad 的通知「已启用」，却在把新的开始菜单快捷方式登记进应用列表（`Get-StartApps`）之前静默丢掉它的通知——同一台机器上用 PowerShell 自己的 id 能弹出来，用 `com.squad.desktop` 不行，Electron 那边仍报告「已显示」。这台机器的应用列表看起来要到下次登录才刷新，所以通知要那之后再确认。

## 29. 一支团队下的多场会话（2026-10-22）

盘点时把 2.x 的 `sitting` 当成只为 dsh 存在的东西去掉了；实际用起来，「同一队人、同一个项目，另起一段讨论」是独立的需求（用户反馈）。做法：

- **一场会话按团队存**：自己的 `teams/<id>/`（记录、用量、席位的 CLI 会话、议程、折叠），加一个 `baseTeamId` 指向它所属的团队（第一场的 id）。table 里其余代码照旧按 id 工作，不用改。
- **共用的六样**：名册、项目文件夹、提示词、资料、团队名、折叠阈值（`table/sessions.ts` 的 `SHARED_FIELDS`）。所有写入都经过 table 的 `save`，它把这六样同步给同队的其他场；比较先按引用，资料可能几十万字。
- **名册只能在全队都停着时改**：席位的窗口在一轮开始时就取好了，别的场正在跑时换人，那一场会少人或多人。
- **关掉一场**和解散一样只是收起，记录留在磁盘上；最后一场不能关，整队收起用「解散」，解散会收起所有场。
- **排序按团队**，一队的几场跟着第一场走。
- **界面**：左栏团队下面缩进列出各场和「＋ 新会话」，只在打开的那一队展开，其他队显示场数；标题旁写当前是哪一场。
